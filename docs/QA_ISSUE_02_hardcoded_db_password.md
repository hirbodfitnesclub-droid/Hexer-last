# 🐛 پیشنویس مورد اصلاحی ۰۲ — پسورد دیتابیس هاردکد در دو فایل tracked

**تاریخ ثبت:** 2026-08-23
**شدت:** 🔴 بالا (اعتبارنامه‌ی واقعی در تاریخچه‌ی git)
**وضعیت:** ⚠️ **ریسک پذیرفته‌شده — تصمیم آرش، 2026-08-24:** rotation انجام نمی‌شود (پروژه‌ی landing در دسترس نیست و ریسک پذیرفته شد). هیچ اقدام فنی لازم نیست؛ این سند صرفاً ثبتِ رسمی پذیرش ریسک است. مورد مرتبط: anon key قدیمیِ حذف‌شده از سورس ولی موجود در git history هم به همین شکل «ریسک پذیرفته‌شده» اعلام شد.
**کشف توسط:** subagent docs-config-qa؛ بازتأیید مستقل توسط main session

---

## ۱. مشکل چیست؟

پسورد Postgres برای role ی `mkt_bridge_user` (پل FDW بین پروژه‌ی اصلی Hexer و پروژه‌ی جداگانه‌ی landing/analytics) **به‌صورت هاردکد** در دو فایل git-tracked است:

- `supabase/sql/36_marketing_fdw.sql:43`
- `landing_supabase/sql/01_analytics_schema.sql:46`

هر کسی که به repo دسترسی داشته باشد (clone/fork/همکار) پسورد را می‌بیند. چون فایل‌ها در **HEAD** هم هستند، merge کردن چیزی را بدتر نمی‌کند — مشکل از الان در تاریخچه‌ی git است.

## ۲. چطور کشف شد؟

subagent دسته‌ی docs/config در حال grep اسرار، الگو را در دو فایل SQL پیدا کرد. من (main session) مستقل بازتأیید کردم:

```
sed -n '43p' supabase/sql/36_marketing_fdw.sql →
  v_password := COALESCE(v_password, 'SecureBridg***REDACTED***');   ← مقدار واقعی ۲۴ کاراکتری
git ls-files → هر دو فایل tracked هستند
git cat-file -e HEAD:... → YES in HEAD
```

نکته‌ی مهم: Vault زنده‌ی production secret با نام `analytics_fdw_password` دارد که طولش **۱۰ کاراکتر** است ≠ پسورد کامیت‌شده (۲۴ کاراکتر). یعنی مسیر consumer حداقل یک بار rotate شده و از fallback هاردکد استفاده نمی‌کند. اما **valid بودن پسورد قدیم روی پروژه‌ی landing** (سمتی که role در آن ساخته می‌شود) از این پروژه قابل تأیید نیست.

## ۳. ریشه

SQL file ها با مقدار fallback برای «راحتی راه‌اندازی» نوشته شده‌اند و هرگز حذف نشدند. session-log خود تیم هم این را به‌عنوان آیتم «Phase 0 — Rotate the committed privileged credentials» شناسایی کرده ولی شاهد تکمیل rotation سمت landing وجود ندارد.

## ۴. اولویت حل

| # | اقدام | توضیح |
|---|-------|-------|
| 1 | **Rotate پسورد روی پروژه‌ی landing** | تنها اقدام مؤثر. اگر پسورد قدیم invalid شود، افشاشده بی‌اثر می‌شود |
| 2 | حذف مقدار از دو فایل + جایگزینی با env/Vault-only | جلوگیری از تکرار |
| 3 | (اختیاری، سنگین) پاکسازی تاریخچه‌ی git | فقط اگر repo قرار است عمومی شود یا همکاران خارجی دارند |

**چرا مهم است:** تا وقتی rotate نشده، این کلید ورود مستقیم به یک دیتابیس Supabase دیگر است.

## ۵. نکته‌ی مرتبط

cron چهارمی (`mkt_refresh`, هر ۳۰ دقیقه) روی production فعال است که در هیچ سندی ذکر نشده و به همین پل FDW مربوط است — باید در RELEASE_BASELINE ثبت شود.
