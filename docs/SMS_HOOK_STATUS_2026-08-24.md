# وضعیت SMS Hook — گزارش تشخیص و تعمیر (2026-08-24)

**مرتبط با:** [QA_ISSUE_06 مورد C](QA_ISSUE_06_edge_functions.md) (fail-open)
**وضعیت:** بخش امنیتی حل شد ✅ — یک باگ عملکردی باقی مانده ⚠️ (نیاز به فیکس کد + deploy)

---

## خلاصه برای کسی که این را بعداً می‌خواند

پیامک OTP (ثبت‌نام/فراموشی رمز) در Hexer از حدود ۱۹ آگوست کار نمی‌کرد. ریشه پیدا شد،
بخشی از آن همین امروز رفع شد، و یک باگ کد باقی مانده که قبل از merge باید فیکس و دیپلوی شود.

## زنجیره‌ی ارسال پیامک در Hexer

```
کاربر فرم ثبت‌نام/فراموشی رمز را پر می‌کند
  → Supabase Auth (/auth/v1/otp یا /auth/v1/signup)
  → Supabase به‌جای ارسال مستقیم SMS، هوک Send SMS را صدا می‌زند (درخواست امضاشده با Standard Webhooks)
  → Edge Function «sms-hook» امضا را چک می‌کند، مالکیت شماره را بررسی می‌کند، cap 3/10min دارد
  → کاوه‌نگار (قالب hexer-verify) پیامک را می‌فرستد
```

## چه چیزی خراب بود — دو مشکل جدا

### مشکل ۱ (حل شد): نبودِ `SEND_SMS_HOOK_SECRET`
- تابع اگر این سکرت را نداشته باشد، درخواست **بدون بررسی امضا** می‌پذیرد (fail-open — همان ISSUE_06-C). امنیتی بود، نه علت قطعی پیامک.
- **رفع شد 2026-08-24:** داشبورد ← Authentication ← Hooks ← Send SMS ← دکمه‌ی Generate خود سوپابیس مقدار `v1,whsec_...` ساخت؛ همان مقدار عیناً در Edge Functions ← sms-hook ← Secrets با نام دقیق `SEND_SMS_HOOK_SECRET` (مفرد) ذخیره شد → redeploy خودکار.
- نتیجه: از این لحظه تابع fail-closed عملاً فعال است (درخواست بی‌امضا reject می‌شود).

### مشکل ۲ (باقی مانده ⚠️): OTP برای «شماره‌ی جدید» شکست ۴۰۳ می‌خورد
**ریشه:** نسخه‌ی جدید sms-hook (v7، دیپلوی ۲۰۲۶-۰۸-۱۹) پیش از ارسال پیامک، وجود کاربر را
با `auth.admin.getUserById` چک می‌کند ([index.ts:62-65](../supabase/functions/sms-hook/index.ts)). اما سوپابیس در مسیر
ثبت‌نام/OTP، شناسه‌ی کاربر را **قبل از ذخیره‌ی دائمی** در دیتابیس به هوک می‌دهد؛ پس چک وجود،
۴۰۴ می‌گیرد و تابع ۴۰۳ برمی‌گرداند → Supabase کل درخواست را با خطای
`Unexpected status code returned from hook: 403` می‌بندد. نسخه‌های قدیمی‌تر این چک را نداشتند — برای همین «قبلاً کار می‌کرد».

## شواهد خام ([VERIFIED-LIVE] — همه فقط-خواندنی به‌جز تست‌های کاربر)

1. **تست زنده‌ی سلامت تابع** (پیلود ساختگی UUID ناموجود، بدون اثر جانبی):
   `POST /functions/v1/sms-hook → HTTP 403 {"error":"Recipient mismatch"}` — یعنی تابع بالنده، `KAVENEGAR_API_KEY` ست است، و (قبل از ست‌شدن سکرت) مسیر بدون‌امضا باز بود.
2. **لاگ لحظه‌ی تست کاربر (۰۶:۳۱:۲۲ UTC):**
   `POST /auth/v1/otp → 500` و بلافاصله `GET /auth/v1/admin/users/7d4a4eee-… → 404` — کاربر در `auth.users` هم وجود نداشت (با SELECT مستقیم تأیید شد).
3. **تست انسانی بعد از ست‌شدن سکرت:** فراموشی رمز با شماره‌ی موجود → **پیامک رسید ✅** (مسیر هوک→کاوه‌نگار سالم است).
4. جدول `sms_hook_deliveries` از ۱۹ آگوست صفر ردیف داشت؛ آخرین ثبت‌نام موفق موبایلی: ۲۳ جولای (قبل از دیپلوی v7).

## کارهای باقی‌مانده (قبل از merge الزامی)

1. **فیکس کد sms-hook** (یک دیپلوی، هر دو مورد):
   - **باگ OTP شماره‌ی جدید:** وقتی درخواست امضای معتبر دارد ولی کاربر هنوز در DB نیست، پیامک ارسال شود (اعتبار امضا جایگزین چک مالکیت می‌شود؛ cap و replay-guard سر جایشان). کاربر ناموجود + امضای نامعتبر → 403 مانند قبل.
   - **fail-closed صریح (ISSUE_06-C):** اگر `SEND_SMS_HOOK_SECRET` غایب بود، به‌جای پذیرش بدون امضا، خطای ۵۰۰ داده شود تا پاک‌شدن تصادفی سکرت بی‌سروصدا حفره نشود.
2. **تست‌های انسانی بعد از دیپلوی** (فقط آرش): ثبت‌نام با شماره‌ی جدید → پیامک باید برسد و حساب ساخته شود؛ فراموشی رمز با شماره‌ی موجود → همچنان سالم؛ تلاش بدون امضا با curl → باید 500/403 بگیرد نه 200.
3. یادآوری بهداشتی: مقدار سکرت در چت اشتراک‌گذاری شده بود؛ هر زمان خواستی از دکمه‌ی Generate صفحه‌ی هوک regenerate کن و مقدار جدید را در Secrets تابع هم آپدیت کن (هر دو جا باید یکی باشند).
