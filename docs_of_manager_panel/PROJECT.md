# PROJECT.md — ستاره قطبی پروژه (Hexer Admin Panel)

> این سند توسط «معمار ارشد سیستم» تولید شده و مرجع نهایی تصمیم‌گیری برای مدل کدنویس است. هر تضادی بین کد و این سند، به نفع این سند حل می‌شود.

## ۱. هدف بیزینس
پنل مدیریت (Admin Dashboard) برای وب‌اپ «Second Brain» با نام **Hexer**. این پنل به مالک محصول اجازه می‌دهد کاربران، اشتراک‌ها، پرداخت‌ها و کدهای تخفیف را که در بک‌اند **Supabase** ذخیره شده‌اند مشاهده و مدیریت کند. این پنل خودش محصول نهایی نیست؛ یک ابزار داخلیِ تک‌کاربره برای اپراتور است.

## ۲. پرسونای هدف
یک اپراتور/ادمین واحد (مالک پلتفرم). محیط اجرا **خصوصی و امن** است و فقط در دسترس مالک قرار دارد. بنابراین UX پیچیده‌ی چندنقشی، مدیریت دسترسی سطحی، و auth سنگین لازم **نیست**.

## ۳. پشته تکنولوژی (Tech Stack) — تثبیت‌شده
- **Frontend:** React 19 + TypeScript + Vite 6 (SPA، بدون SSR، بدون Next.js)
- **Styling:** Tailwind CSS v4 (پیکربندی توکن‌ها در `src/index.css` با بلاک `@theme`؛ بدون `tailwind.config.js`)
- **State:** Zustand (`src/store/adminStore.ts`)
- **Charts:** Recharts v3
- **Animation:** `motion` (نسخه‌ی جدید framer-motion)
- **Notifications:** `react-hot-toast`
- **Icons:** `lucide-react`
- **Backend:** Supabase (Postgres + Auth + Edge Functions با Deno + pgvector + Storage)
- **Gateway پرداخت:** Zibal (در Edge Functions موجود)
- **AI:** Google Gemini (در Edge Functions موجود — خارج از scope این پنل)

## ۴. تشخیص ریشه‌ای مشکل فعلی (Root Cause Analysis)
خطای کنسول `Forbidden use of secret API key in browser` به یک علت بنیادین برمی‌گردد:

1. **علت اصلی:** کلید **secret** سوپابیس (`sb_secret_...`) مستقیماً در مرورگر استفاده شده است (هم در `src/lib/supabase.ts` و هم در `src/lib/dataStore.ts`). سیستم کلیدهای جدید سوپابیس استفاده‌ی کلید secret را از داخل مرورگر **به‌صورت سخت‌افزاری مسدود** می‌کند؛ پس هیچ درخواست داده‌ای موفق نمی‌شود. این مشکل با «هاردکد کردن کلید» قابل‌حل نیست چون مشکل امنیتیِ صرف نیست، یک بلاک فنیِ سمت سوپابیس است.

2. **علت بنیادین دوم:** این یک پنل ادمین است و باید **همه‌ی ردیف‌های همه‌ی کاربران** را بخواند، در حالی‌که تمام جداول دارای RLS با شرط `auth.uid() = user_id` هستند. حتی اگر کلید anon/publishable در مرورگر استفاده شود، به‌دلیل نبودِ سشن کاربر، RLS همه‌چیز را خالی برمی‌گرداند.

3. **علت بنیادین سوم:** ایمیل کاربران در `auth.users` است نه در `public.profiles` و از طریق PostgREST اصلاً قابل خواندن نیست. مسدودسازی کاربر هم ستون `is_blocked` ندارد و فقط با Admin API (`auth.admin`) ممکن است. پس بخشی از قابلیت‌های فعلیِ UI **ذاتاً نیازمند دسترسی service_role در سمت سرور** است.

**نتیجه‌ی معماری:** تنها راه‌حلِ اصولی، مدرن و حداقلی، انتقال تمام عملیات‌های privileged به یک **Edge Function واحد به‌عنوان Gateway ادمین** است که با service_role کار می‌کند و با یک رمز ادمین ساده محافظت می‌شود. کلید secret باید کاملاً از مرورگر حذف شود.

> **تطبیق با درخواست کاربر:** کاربر گفت «هاردکد کردن کلید اشکالی ندارد». این پذیرفته می‌شود، اما کلید secret به‌هیچ‌وجه نباید در مرورگر بماند (فنی غیرممکن است). در عوض، رمز ادمینِ ساده در فرانت هاردکد می‌شود و کلید service_role فقط در Secrets خودِ Edge Function (سمت سرور سوپابیس) قرار می‌گیرد. این هم ساده است و هم واقعاً کار می‌کند.

## ۵. [حیاتی] نبایدهای سخت‌گیرانه (Anti-Patterns)
مدل کدنویس باید بی‌چون‌وچرا از این فهرست اطاعت کند:

- **ممنوع:** استفاده از کلید `sb_secret_...` یا هر service_role key در هیچ فایلی زیر `src/`. این کلید فقط در Edge Function مجاز است.
- **ممنوع:** زدنِ مستقیمِ PostgREST (`/rest/v1/...`) از مرورگر برای داده‌های ادمین. تمام دسترسی داده‌ی پنل باید از طریق Edge Function `admin-api` عبور کند.
- **ممنوع:** افزودن ORM (Prisma/Drizzle) یا کلاینت SQL مستقیم. از کلاینت رسمی `@supabase/supabase-js` فقط داخل Edge Function استفاده شود.
- **ممنوع:** ساختنِ سرور Express/Node جداگانه. زیرساخت سروری ما فقط Supabase Edge Functions است (هرچند `express` در dependencies هست، استفاده نشود و به آن تکیه نکنیم).
- **ممنوع:** تغییر مدل RLS جداول یا غیرفعال‌کردن RLS برای راحتیِ پنل. RLS دست‌نخورده می‌ماند؛ پنل از طریق service_role آن را bypass می‌کند.
- **ممنوع:** مهاجرت به Next.js، افزودن react-router، یا تغییر بنیادین معماری SPA فعلی (روتینگ از طریق `activeTab` در Zustand کافی است).
- **ممنوع:** CSS خطی یا فایل CSS جدید؛ فقط کلاس‌های Tailwind و توکن‌های تعریف‌شده در `src/index.css` (مثل `slate-*` و `brand-*`).
- **ممنوع:** افزودن کتابخانه‌ی تاریخ سنگین (moment/dayjs) — از `Intl`/`toLocaleDateString('fa-IR')` که الان استفاده می‌شود ادامه دهید.
- **ممنوع:** over-engineering — نه auth کامل سوپابیس برای ادمین، نه RBAC، نه میکروسرویس. یک Gateway واحد + رمز ادمین کافی است.
- **ممنوع:** تغییر منطق فایل‌های SQL موجود (`00`..`23`). تغییرات اسکیمایی فقط در یک فایل migration **جدید** اضافه می‌شوند (idempotent).
- **اجباری:** خروجی Edge Function باید دقیقاً منطبق با تایپ‌های TypeScript موجود در `src/lib/supabase.ts` باشد (الگوی Anti-Corruption Layer)، تا تغییرات فرانت حداقلی بماند.

## ۶. تعریف «انجام‌شده» (Definition of Done)
- پنل پس از لاگین، لیست واقعی کاربران/اشتراک‌ها/پرداخت‌ها/کدهای تخفیف را از سوپابیس نمایش می‌دهد.
- هیچ خطای `Forbidden use of secret API key` یا خطای دیگری در کنسول نیست.
- ویرایش پروفایل، مسدودسازی/رفع‌مسدودی کاربر، تغییر/تمدید اشتراک، و CRUD کدهای تخفیف واقعاً در دیتابیس اعمال می‌شوند.
- اخطار `width(-1) and height(-1) of chart` برطرف شده است.
- هیچ کلید secret در bundle فرانت وجود ندارد.

## ۷. سیستم پرداخت کارت به کارت و رسید آفلاین (Offline Card-to-Card & Receipt System)

برای ارتقای جریان درآمد پایداری در دوران قطعی احتمالی درگاه پرداخت زیبال و جلوگیری از هدر رفت ظرفیت رایگان فضای ذخیره‌سازی سوپابیس، سیستم جایگزین کارت به کارت همراه با آپلود رسید طراحی شده است که فلوهای آن در زیر تشریح می‌شود:

### الف) فلو و ضوابط سمت کلاینت کاربر (Hexer AI Client Flow)
۱. **انتقال UI اشتراک‌ها**: بخش اشتراک‌ها نباید مستقیماً در قالب سه باکس باز نمایش داده شود. بلکه دکمه ورود به اشتراک‌ها در «مودال پروفایل کاربر» تعبیه می‌شود. کاربر با زدن روی آن ابتدا جزییات سطح اشتراک جاری خود را دیده و بسته به وضعیت فعال یا Expired بودن، دکمه‌های مناسب «تمدید» یا «خرید» را که منتهی به لیست پلن‌ها می‌شود مشاهده می‌کند.
۲. **مودال تراکنش و تخفیفات**: پس از کلیک روی بسته‌ مورد نظر، مودال چندگزینه‌ای «انتخاب شیوه پرداخت» گشوده شده و در آن فیلد درج کد تخفیف قرار می‌گیرد. در فرضی که اعمال کوپن باعث رسیدن فاکتور به ۱۰۰٪ تخفیف شود، جریان بانکی کاملاً دور زده شده (Bypass) و اشتراک مستقیماً در دیتابیس فعال می‌شود. در غیر این صورت دو دکمه «پرداخت آنلاین زیبال» و «کارت به کارت (آفلاین)» برای انتخاب باز است.
۳. **قوانین ذخیره و فشرده‌سازی لایو رسیدها**: در الگوی کارت به کارت، کاربر موظف به فرمت تصویر فیش یا رسید پرداختی است. جهت ممانعت از پر شُدن سریع فضای رایگان Supabase Storage، محدودیت حجم فایل ورودی حداکثر روی ۲ مگابایت قفل می‌شود و المان آپلود کلاینت موظف است قبل از ارسال هر تگ سند، تصاویر را فشرده کرده و حجم کل را به کم‌تر از ۵۰۰ کیلوبایت برساند.
۴. **تثبیت استیت «در انتظار تایید»**: بعد از ثبت فیش رسید تراکنش، استاتوس اشتراک بلافاصله روی وضعیت `'pending_manual'` یا «در انتظار تایید» قفل گردیده و در این حالت کاربر تا دریافت رای هیات بازرسی، حق فرستادن تراکنش تکراری یا دکمه‌های انصراف و لغو اشتراک را ندارد.
۵. **رزرو آنی ظرفیت کوپن**: هنگام سابمیت شیوه کارت به کارت، در فرضی که کاربر کوپن فعال وارد کرده باشد، برای پیشگیری از نشت همزمانی ظرفیت فراتجسمی کوپن در فاصله‌ی بررسی آفلاین ادمین، سهمیه استفاده شده از فیلد کد تخفیف موقتاً در دیتابیس رزرو و کسر می‌شود.
۶. **فیدبک مخالفت ادمین**: در صورتی که ناظر درخواست را رد کند، کاربر پس از لود مجدد بخش اشتراک‌ها با بنر یا آلرت قرمز رنگ حاوی «علت رد شدن درخواست» مواجه شده و پس از نشان دادن این فیدبک، مجدداً دکمه‌های خرید فعال شده و جریان ثبت‌نام برای وی از دست‌انداز بایکوت خارج می‌گردد.

### ب) فلو و ضوابط مدیریت سمت پنل ادمین (Manager Panel Flow)
*توجه: همه‌ی جزییات تسک‌ها، کنترلرها و آپدیت کدهای مرتبط با این بخش بنابر قواعد معمار در پوشه اختصاصی `docs_of_manager_panel` قرار می‌گیرند.*
۱. **پورتال بازرسی رسیدهای آفلاین**: افزودن بخشی مجزا جهت مانیتور، مرتب‌سازی و پایش لیست درخواستی‌های رسید کارت به کارت کاربران همراه با آدرس زنده فایل رسید شات، مِتریک تومان و شناسه فرد.
۲. **فرآیند موافقت (Approve Action)**: پس از زدن روی دکمه سبز تایید، اشتراک به شکل رسمی برای کاربر فعال می‌گردد و همگام با این فرآیند، فیش امانی آپلود شده باید در همان ثانیه برای همیشه از گیت Supabase Storage حذف گردد تا فضا کاملاً باز شود.
۳. **فرآیند مخالفت (Reject Action)**: با کلیک روی فیلد رد درخواست، مودال ابطال باز شده و ادمین می‌تواند علت رد را ویرایش کند (به همراه یک متن پیش‌فرض پیش‌نویس عمومی). پس از اعمال رد:
   - عکس رسید پرداختی فوراً از Supabase Storage پاک می‌شود.
   - رزرو ظرفیت کوپن کد تخفیف با افزودن شارژ مجدد به آیدی فیلد مربوطه به پایگاه داده پس داده می‌شود تا دیگر کاربران از سهمیه محروم نشوند.
   - متن توجیهی علت رد تراکنش در سوابق ذخیره می‌شود تا کاربر در کلاینت خود بنر را دریافت کند.
